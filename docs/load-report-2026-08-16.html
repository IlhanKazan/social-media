Mixed workload flagship

Four user types run concurrently at the ratio a social feed actually sees. Each virtual user performs a whole session — open the feed, scroll, tap into a thread, read replies, visit the author — because a sequence is what exposes N+1 queries and cache misses. A single-endpoint loop cannot.

Why per-endpoint gates. An aggregate p95 lets a slow write path hide behind a large volume of fast reads. That is how a load test goes green while the product feels broken.

Throughput ceiling open model

Driven by arrival rate, not by a fixed pool of users. A closed model self-throttles: when the server slows, virtual users wait, offered load quietly drops, and the server appears to "handle" a rate it never actually faced.

The binding constraint here is the application's own rate limiter, not the server. /posts/explore is capped at 120 req/min per user, so admitted traffic tops out near pool × 2 req/s. Latency stayed flat to the ceiling — the server never became the bottleneck.

Real-time sessions STOMP over WebSocket

Request throughput says nothing about how many simultaneous connections the app can hold. Each session pins a socket, a registry entry and broker subscriptions for its whole lifetime, so the limiting resource is concurrency over time.

What this does not prove

A benchmark without its caveats is marketing. These are the limits of the run above.

  • Shared hardware. k6 and the API ran on one machine and competed for CPU. Dedicated infrastructure would typically improve these figures, not worsen them.
  • Local Postgres. Faster than a small managed instance. Database-bound paths would degrade first under production storage.
  • The ceiling is a policy, not a limit. Rate limiting stopped the capacity ramp before the server strained, so no CPU or connection-pool saturation point was found. Raw headroom is untested.
  • Seeded dataset. 51 accounts and 330 posts. Query plans that only degrade at millions of rows would not appear here.
  • Single instance. No horizontal scaling, no cross-node cache or rate-limit coordination was exercised.
Superseded figures. An earlier run recorded ~490 req/s. Per-user rate limiting was added to the read path hours after that measurement, so the number cannot be reproduced on current code and is not quoted here.

Method

  1. Rebuild the API image from source — a cached image will silently benchmark an old build.
  2. Reset the database so the seeder populates a known dataset: 51 accounts, 330 posts, a follow graph.
  3. Authenticate a pool of 50 distinct users, each on its own forwarded address, so per-user rate limits do not collapse the pool to a single bucket.
  4. Run each scenario against the container network, with dependencies pinned so nothing restarts mid-run.
  5. Gate on per-endpoint latency, completed journeys and auth failures; track 429s separately as limiter behaviour rather than error.
